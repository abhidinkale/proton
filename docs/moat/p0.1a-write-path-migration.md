# P0.1a — moving the clinical trio off SQLite

**Status:** staged; commit 1 applied. The v9 `clinic_desk_fields` migration is
in `db/workflowMigrations.js` and is asserted by
[`workflow_sign_safety_validation.cjs`](../../apps/api/tests/workflow_sign_safety_validation.cjs).
The backfill, the Postgres repository, and the switch have not been executed.
**Scope:** `clinic_patients`, `clinic_appointments`, `clinic_notes` → Postgres.
**Out of scope for P0.1a:** notifications, invoices, preferences, the audit
chain. Those stay in SQLite and are explicitly labelled non-clinical legacy
until P0.1b.

The reason for the split is risk, not elegance. The clinical trio is what the
doctor reads and signs; it is also what the backup, the state machine, and the
attestation need. The other four tables are admin surface. Moving all seven at
once is how the demo breaks in front of a design partner.

---

## 1. What is there today

`apps/api/storage/clinicRepository.js` (1,503 lines) owns seven SQLite tables
and 33 routes under `/api/clinic`:

| SQLite table | Rows used by | Clinical? |
|---|---|---|
| `clinic_patients` | chart, queue, sign | yes |
| `clinic_appointments` | schedule, booking, queue | yes |
| `clinic_notes` | draft, sign, report, audit | yes |
| `clinic_notifications` | attention queue | no |
| `clinic_invoices` | billing | no |
| `clinic_meta` | preferences, education | no |
| `clinic_audit_events` | audit, verify | no (but trust-relevant) |

The sign path is `clinicRepository.signNote` → SQLite. It now runs
`SafetyGate` and stores the verdict (P0.8), but the note and the verdict are
still outside the Postgres backup and outside tenant RLS.

## 2. Target shape

The Postgres workflow schema already has `patients`, `appointments`, `notes`,
`encounters`, `diagnoses`, `prescriptions`, `reports`, `outbox`, and
`workflow_audit_events`. The clinical trio maps onto the first three. Two
additions are needed for fields the workflow schema does not carry:

```sql
-- v9_clinic_desk.sql
ALTER TABLE patients
  ADD COLUMN IF NOT EXISTS clinical_profile JSONB NOT NULL DEFAULT '{}'::jsonb;

ALTER TABLE appointments
  ADD COLUMN IF NOT EXISTS queue_category TEXT,
  ADD COLUMN IF NOT EXISTS priority TEXT NOT NULL DEFAULT 'normal',
  ADD COLUMN IF NOT EXISTS metadata JSONB NOT NULL DEFAULT '{}'::jsonb;

ALTER TABLE notes
  ADD COLUMN IF NOT EXISTS title TEXT,
  ADD COLUMN IF NOT EXISTS legacy_signed_at TIMESTAMPTZ;
```

`clinical_profile` holds the fields the cohort JSON carries today: allergies,
conditions, medications, vitals, recent labs, clinical history, missing
information. It is deliberately JSONB for the migration; the structured note
schema is the long-term home for the parts that matter (P0.3).

No new `clinic_*` tables for the clinical trio. IDs are preserved as TEXT.

## 3. Field mapping

### `clinic_patients` → `patients`

| SQLite | Postgres | Rule |
|---|---|---|
| `id` | `id` | preserved |
| `tenant_id` | `tenant_id` | preserved |
| `name` | `full_name` | preserved |
| `mrn` | `mrn` | preserved |
| `data_json.dob` | `date_of_birth` | parse ISO; invalid → null, log |
| `data_json.gender` | `sex` | lowercase; unknown → null |
| `data_json` | `clinical_profile` | whole object, minus dob/gender |
| `created_at`, `updated_at` | same | preserved |

### `clinic_appointments` → `appointments`

| SQLite | Postgres | Rule |
|---|---|---|
| `id` | `id` | preserved |
| `patient_id` | `patient_id` | must exist after patient backfill |
| `date` + `time` | `scheduled_for` | parse in the clinic's timezone; reject ambiguous |
| `duration_minutes` | `duration_minutes` | default 30 |
| `status` | `status` | map `COMPLETED`/`CANCELLED`/`NO_SHOW`; else `BOOKED` |
| `queue_category` | `queue_category` | preserved |
| `priority` | `priority` | preserved |
| `data_json` | `metadata` | whole object minus mapped fields |
| `created_at`, `updated_at` | same | preserved |

`appointments` requires `clinician_id`; the SQLite row has it only inside
`data_json`. The backfill must resolve it from `data_json.clinicianId`, or use
the seeded clinician as a last resort and record that in `metadata.backfill_warning`.

### `clinic_notes` → `notes`

| SQLite | Postgres | Rule |
|---|---|---|
| `id` | `id` | preserved |
| `patient_id` | resolve to an `encounter_id` | create one encounter per legacy note if none exists |
| `data_json` | `content` | preserved JSONB |
| `status` | `status` | `DRAFT`/`SIGNED`/`AMENDED` map 1:1 |
| `data_json.title` | `title` | |
| `data_json.signature` | `provenance.signature` | preserve; add `backfilled: true` |
| `signed_at` | `legacy_signed_at` | preserve; `notes.signed_at` stays null until re-signed |
| `created_at`, `updated_at` | same | preserved |

**Legacy signed notes are not re-signed.** Their signature was made over a
different canonical form (there was none). The migration preserves it as
historical data and marks it `signature.backfilled = true`; it does not mint an
`attest_v1` record for it. Only new signatures produce attestations.

## 4. Backfill

Order: patients → appointments → notes → encounters for notes.

```sql
-- 1. patients
INSERT INTO patients (id, tenant_id, full_name, mrn, date_of_birth, sex, clinical_profile, created_at, updated_at)
SELECT id, tenant_id, name, mrn, ..., ..., data_json::jsonb, created_at::timestamptz, updated_at::timestamptz
FROM legacy_clinic_patients
ON CONFLICT (id) DO NOTHING;

-- 2. appointments (after clinician resolution)
-- 3. notes (create encounters where missing)
```

The backfill runs as a one-shot script inside a transaction, writes a
`backfill_report` row (counts, skipped rows, warnings), and is idempotent:
`ON CONFLICT DO NOTHING`, then a second pass that reports mismatches.

### Verification

- Count equality per table.
- A sample of 20 notes: `content` JSONB deep-equals the SQLite `data_json`.
- Every note has an encounter; every encounter has a patient.
- The audit chain is **not** backfilled; the SQLite chain remains the historical
  record. New Postgres audit events start at a new genesis and say so.
- A restore drill restores the Postgres note and its signature.

## 5. Read/write switch

One flag, one repository:

```text
PROTON_DESK_BACKEND=sqlite | postgres
```

`storage/postgresClinicRepository.js` implements the same public functions as
`clinicRepository.js` for the clinical trio. The route chooses at mount time:

```js
const clinic = process.env.PROTON_DESK_BACKEND === 'postgres'
  ? require('../storage/postgresClinicRepository')
  : require('../storage/clinicRepository');
```

### Dual-read comparison

Before flipping writes:

1. Backfill.
2. Read both stores on `/overview`, `/patients`, `/patients/:id`,
   `/appointments`, `/notes`.
3. Compare a normalized shape; log the first 20 diffs per endpoint.
4. No `PROTON_DESK_BACKEND=postgres` until the diff is empty on the demo cohort.

### Writes

- Create/update patient → Postgres.
- Create/update appointment → Postgres.
- Save draft → Postgres `notes`.
- Sign → Postgres `notes` + `transitionEncounter('sign')` + attestation.
- Notifications/invoices/preferences stay SQLite, keyed by the same IDs. They
  are non-clinical and are labelled as such in the admin UI.

### Rollback

The flag flips back to SQLite. Do not delete the SQLite clinical tables until
the demo passes on Postgres and one real desk day completes without a diff.
Rollback is a flag, not a restore.

## 7. Risks and what the migration does not solve

- **JSON shape drift.** `data_json` was never schema-validated. The backfill
  preserves it; `note_v1` validation is P0.3, not this cut.
- **Legacy signatures are not `attest_v1`.** They are historical; do not claim
  otherwise.
- **Audit continuity.** The SQLite chain and the Postgres chain are separate.
  The trust pack must say which chain covers which period.
- **Notifications referencing notes.** They stay in SQLite by ID; a note moved
  to Postgres with the same ID keeps the reference. If an ID ever changes, the
  notification is orphaned; the backfill must not rewrite IDs.
- **Billing/invoices** remain SQLite and are out of scope. Do not describe the
  desk as "fully Postgres" until P0.1b.
- **The workflow `sign` path is already gated** (P0.8); the clinic path is the
  one moving.
