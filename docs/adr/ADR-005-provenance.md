# ADR-005: Cryptographic AI Provenance System & Lifecycle Badges

## Status
Accepted

## Context
Proton maintains a strict invariant: **AI output is never clinical fact until physician approval.**
Currently, provenance tracking is split between:
* `auditService.js` (tamper-evident SHA-256 event chaining).
* In-memory UI flags in `apps/web/src/components/ui/ProvenanceBadge.tsx` (`AI DRAFT — REVIEW REQUIRED`, `DOCTOR EDITED`, `CONFIRMED CLINICAL DATA`).
* Task metadata in `storage/taskRepository.js`.

As we introduce specialist agents, multi-agent orchestration, and external model providers, we need a unified backend `ProvenanceSystem` to stamp every AI draft with an immutable provenance envelope before it reaches the frontend or persistent storage.

## Decision
Create `ProvenanceSystem` in `apps/api/services/clinical/provenanceSystem.js`:
1. **Canonical AI Provenance Envelope:**
   ```typescript
   interface AIProvenance {
     provenanceId: string;
     generatedBy: "AI";
     agentId: string;
     specialty?: string;
     modelId: string;
     modelVersion: string;
     generatedAt: string;
     inputDigest: string;           // SHA-256 of input prompt / clinical context
     sources: Array<{               // Traceable citations to patient record or guidelines
       resourceType: string;
       id: string;
       quote?: string;
       authority?: string;
     }>;
     status: "DRAFT" | "REVIEWED" | "EDITED" | "ACCEPTED" | "REJECTED" | "APPROVED";
     physicianId?: string;
     physicianActionAt?: string;
     directiveOverride?: string;
     tamperHash: string;            // SHA-256 signature sealing the provenance record
   }
   ```
2. **Lifecycle State Machine:**
   * `DRAFT`: Initial state generated by AI agent or model.
   * `REVIEWED`: Viewed by physician.
   * `EDITED`: Modified by physician.
   * `ACCEPTED` / `APPROVED`: Explicitly authorized by authenticated physician.
   * `REJECTED`: Explicitly dismissed by physician (omitted from patient handoff).
3. **Integration with `auditService`:**
   * Every status transition triggers an immutable audit log entry in the cryptographic hash chain.
   * Client-side attempt to fake `status: APPROVED` without physician credentials is rejected.

## Alternatives Considered
1. *Store provenance as arbitrary JSON string in FHIR note:* Rejected because provenance must be queryable and tamper-evident across audit reviews.
2. *Rely solely on UI state management:* Rejected because backend security must not trust client-asserted approval status.

## Why This Decision
* Provides end-to-end auditability and legal defensibility for AI-assisted clinical documentation.
* Guarantees 100% adherence to physician review requirements.

## Risks & Mitigations
* *Risk:* Overhead of generating cryptographic hashes for every intermediate draft.
* *Mitigation:* SHA-256 hashing takes < 0.1 ms in Node.js Crypto; zero noticeable latency overhead.

## Migration Strategy
1. Implement `ProvenanceSystem`.
2. Connect `ClinicalPipeline` Stage 6 and `AgentOrchestrator` to generate `AIProvenance` envelopes.
3. Map envelopes to `ProvenanceBadge.tsx` in the web client and `DorkStatusBadge.kt` in the Android app.

## Testing Strategy
* Tamper-detection unit tests (altering payload after hash generation fails validation).
* State transition tests (verifying invalid transitions like `DRAFT -> APPROVED` without physician auth fail).
